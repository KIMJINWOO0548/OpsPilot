# 영수증 누락 시 재실행 차단

## 기준과 변경

공식 원격 `improve/competitive-depth-20261106`의
`1427ff11f01edd486e7e39d62e5a088530015882`에서 만든 독립 증분이다.
새 브랜치는 `improve/execution-recovery-20261109`다. 접근이 거부된 보존본
`b4c3d65`와 Space 파일은 읽지 않았으며, 그 이력의 복구·대체·통합을 의미하지 않는다.

기존 코드는 이미 `UNKNOWN_RECONCILE` 또는 `SUCCEEDED`인 제안도 영수증이 없으면
새 모의 작업을 만들 수 있었다. 이제 영수증 없는 최초 `APPROVED` 상태만 현재
근거·승인을 확인한 뒤 새 작업을 만든다.

| 저장 상태와 영수증 | 실행·복구 결과 |
|---|---|
| `APPROVED`, 영수증 없음 | 기존 현재 권한·근거 검사 후 로컬 모의 작업 1건 생성 |
| `UNKNOWN_RECONCILE`, 영수증 없음 | 불명 상태 유지, 새 작업 0건 |
| `SUCCEEDED`, 영수증 없음 | `UNKNOWN_RECONCILE`로 저장하고 `RECEIPT_UNAVAILABLE` 감사 1건, 새 작업 0건 |
| 기존 영수증 있음 | 기존 영수증 조회로 복구·재시도, 새 작업 생성 없음 |

현재 세션·객체 tenant/team·독립 승인·원 승인자 검사는 불명 상태 처리보다 먼저다.
이미 UNKNOWN인 반복 요청은 영수증 부재만으로 새 감사나 작업을 추가하지 않는다.
기존 정상 성공·복구 요청의 SUCCEEDED/RECONCILED 감사 동작은 유지한다.
UI와 API 응답 필드·DB schema는 바꾸지 않았다.

## 처리 전 장애와 수동 해제 경계

현재 구현의 모의 작업과 상태·감사는 동일 SQLite 트랜잭션에 있다. INSERT 전이나
성공 감사 기록 전 주입한 오류는 전체 rollback을 확인한 뒤 `APPROVED`에서 재시도할
수 있었다. 이는 해당 로컬 트랜잭션에 부작용이 남지 않은 경우의 검증이다.
실제 외부 서비스가 처리했는지 모르는 통신 오류에 이 결론을 적용할 수 없다.

영수증 부재는 미실행의 증거가 아니다. 시간 경과나 반복 실행으로 불명 상태를
자동 해제하지 않으며, 수동 reset/강제 재실행 API도 없다. 원 승인자나 현재 권한을
우회하는 인계 경로를 추가하지 않았다. 처리 결과를 확인할 수 없으면 불명 상태를
유지해야 한다. 향후 수동 해제는 원래 작업 키·영수증과 실제 처리 여부를 별도로
대조하고, 현재 권한·승인·감사 절차를 정의한 뒤 구현해야 한다.

## 실제 검증과 한계

기준 전체 193개와 두 스모크는 통과했다. 새 시험은 수정 전 4 실패/4 통과였고,
수정 후 8개가 통과했다. 전체 201개, 모의 E2E, 작성자 합성 8/8, Ruff,
필수 파일 24개 검사도 통과했다. 기존 Starlette/httpx 경고 1개는 남아 있다.

시험은 임시 synthetic DB에서 영수증을 제거한 복구 손실 상태를 주입하고,
앱 인스턴스를 새로 만들어 execute/reconcile 혼합 동시 재시도·원 승인자 제한·
원래 영수증 재등장 후 복구·알려진 로컬 rollback을 확인한다. 별도 OS 프로세스의
강제 종료나 실제 네트워크 장애를 재현한 시험은 아니다.

실제 외부 작업 서비스·분산 outbox·지속 실행 예약·stale 예약 해제·전체 exactly-once는
구현하거나 검증하지 않았다. Windows·브라우저·Docker·외부 운영 수용·독립 사람 검수도
이번 범위 밖이다. 현재 G2 모의 방어 개선이 G0/G1 연구나 G5 외부 신뢰성 게이트의
완료를 의미하지 않는다. 실행 요약은 `verification/execution-recovery-2026-11-09.json`,
원시 로그는 새 `.local/verification/*-execution-recovery/`에 있다.
