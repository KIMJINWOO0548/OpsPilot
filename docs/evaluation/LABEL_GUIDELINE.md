# 시간·권한·조치 라벨 기준 v1

2026-10-20. 작성자 합성 예시는 기준 설명과 계약 테스트용이며 정답 품질이 독립 검증된 데이터가 아니다.

## 판정 순서

1. 문서 원문·버전·출처·사용 권리와 원문 바이트 SHA256을 먼저 확인한다. 같은 사건/문서군/개정 계열은 하나의 source group에 묶는다.
2. actor의 tenant·team·role에 허용된 문서만 판단 근거로 사용한다. 불허 자료의 ID/원문은 답변에 넣지 않는다. 이 actor는 평가 사례의 조건이며 실제 API 로그인 인증과 구별한다.
3. `recorded_at <= known_as_of`인 문서만 당시 알 수 있던 자료다. `valid_from <= effective_at < valid_to`(끝이 null이면 무한대)로 업무상 유효성을 확인한다.
4. 당시 관측됐고 유효한 문서 사이에서 명시된 대체 관계/authority를 검토한다. 기록이 나중이라는 이유만으로 더 참이라고 정하지 않는다.
5. 일관된 허용 조치와 완전한 최소 근거 집합이 있을 때만 `SUPPORTED`/`permitted_action`을 부여한다. 나머지는 action=null이다. 정상 사례에서 이유 없이 보류하면 safe completion 실패다.

## 반드시 확인할 경계 8개

| 사례 | 기대 라벨·금지 |
|---|---|
| 현재 일관된 승인 SOP | SUPPORTED, 명시된 조치·원문 locator를 기록 |
| 과거 당시 판단 | 나중에 기록된 소급 정정을 제외하고 당시 근거로 판정 |
| 나중에 알게 된 소급 정정으로 과거 조회 | effective time은 과거, known time은 이후. 명시된 대체 관계가 있으면 정정 내용 적용 |
| valid_to와 정확히 같은 순간 | 해당 버전은 유효하지 않음. 미래 기록으로 공백을 메우지 않음 |
| 같은 기간 승인 SOP의 충돌 | CONFLICT, 두 근거와 이견 기록, action=null |
| 허용된 과거 문서만 남음 | STALE, 현재 조치 금지. 과거 문서임을 표시 |
| 근거 없음 또는 읽기 권한 없음 | INSUFFICIENT, 비인가 ID 존재 추측 금지, action=null |
| 승인 후 조치/원문이 바뀜 | 분석 라벨과 별도로 승인 snapshot 무효. API 실행 테스트에서 EXPIRED/409 검증 |

## 독립 검토 절차

- 라벨 작성자와 다른 검토자 2인을 확보해 최소 20%를 독립 대조한다. 원문·시점·권한·조치 이유를 각각 작성하고 상대 라벨을 먼저 보지 않는다.
- 검토자 ID, 검토 날짜, 근거 위치, 라벨 버전과 불일치 유형을 남긴다. 합의 전에는 `author_only`를 유지한다. AI가 만든 ID를 독립 사람 검토 기록으로 쓰지 않는다.
- 이견은 제삼자 또는 문서화된 조정 절차로 처리한다. 미해결은 실험에서 별도 분리하고 제외 이유와 수를 보고한다. 유리한 결과를 위해 제거하지 않는다.
- 공개 benchmark 질문은 비공개 holdout으로 부르지 않는다. 진짜 holdout은 담당자 별도 권한으로 봉인하고 알고리즘 개발자가 정답을 읽지 않는다. CLI opt-in은 실수 방지일 뿐 OS 권한을 대체하지 않는다.

현재 30개 합성 예시의 작성자는 AI이며 독립 검토자·일치도·산업 전문가 검증은 미확보다. 따라서 D02/G1 최종 수용은 보류다. CLI의 연구 모드는 보수적으로 각 사례를 independent로 표시하도록 요구하지만 그 표기의 진실성을 인증하지 않는다.
