# ADR-005 · 같은 업무 시점의 관측 근거 비교

- 날짜: 2026-11-02
- 상태: 구현·로컬 합성 수용 검증 완료; 외부 검증 미실행
- 대상: 사후 정정이 과거 판단에 어떤 차이를 만드는지 확인하는 engineer/approver

## 선택 이유와 대안

현재 `/analysis`는 한 유효 시점·관측 시점의 판정만 반환하고 타임라인은 문서별 시간축만 보여준다. A-104의9월20일 판단과10월5일에 알려진 소급 정정을 비교하려면 사용자가 수동으로 재분석하고 결과를 기억해야 한다. 이 비교를 한 요청·한 화면으로 제공한다.

개발·디자인·독립 QA가 기존 코드와 실제 A-104 흐름을 검토했다. 실행 사전 점검은 기존 `evidence_reviewable`·권한/상태 안내와 겹치고, 설비 영향·비용 시뮬레이션은 입력 모델이 없다. 감사 이력은 요청별로 이미 존재한다. 이번 단위는 bitemporal 핵심 기능인 **고정 유효 시점 + 두 관측 시점의 판정·조치·인용 차이**로 제한한다. 새 엔진·모델·라이브러리·실데이터는 도입하지 않는다.

## 계약과 화면

`POST /api/v1/analysis/compare`는 `asset_id`, `claim_key`, `effective_at`, `before_known_as_of`, `after_known_as_of`를 받는다. 모든 시점은 시간대를 포함하고 관측 시점은 앞뒤 순서를 지킨다. 서버 세션 principal을 사용하며 본문의 actor는 권한을 바꾸지 못한다.

두 관측 시점에 대해 각각 SQL 권한·recorded_at 선필터 후 기존 결정적 판단기를 실행한다. 같은 읽기 전용 DB 트랜잭션을 사용해 비교 중 ACL/문서 변경으로 서로 다른 DB snapshot을 섞지 않는다. 현재 접근 권한을 두 결과에 동일하게 적용하며, 과거 사용자의 실제 권한 이력을 재현한다고 표현하지 않는다.

응답은 `before`, `after`, `changed`, `changes`다. 차이는 상태·조치의 변경 여부와 허용된 인용의 추가/제외 목록이다. 인용 내용 전체의 동일성을 비교하며 관측 시점 숫자만 다르면 변경으로 세지 않는다. 숨겨진 문서의 ID·개수·사유는 반환하지 않는다.

기존 타임라인의 비교 패널에서 기준/비교 관측 시점, 동일한 유효 시점, 두 결과와 인용 차이를 보여준다. A-104 합성 예시를 제공하고 입력 변경·실패·로그아웃 시 이전 결과를 지운다. 비교 결과는 작업 초안 생성이나 승인의 입력으로 연결하지 않는다.

## 수용 조건

1. A-104: 유효9/20 고정, 관측9/20→10/6에서 수동 점검→센서 진단 및 v1→정정 근거 차이를 표시한다.
2. 동일 근거는 변경 없음, A-105 충돌은 보류 상태를 유지한다. 빈 근거는 두 결과에 명확히 표시한다.
3. 인증/CSRF, 현재 ACL 선필터, tenant/team/role 격리, actor 위조 무효, timezone/역순422를 테스트한다.
4. 비교 전후 proposals/work_orders/audit가 동일하고, 응답 유실 상태·기존 영수증 및 정상 복구를 보존한다.
5. 실제 Chromium에서 정상·변경 없음·빈 상태·오류·로딩·입력 초기화·모바일을 검증한다. 기존 API/UI 회귀를 통과한다.

G0/G1 연구 수용·정확도·실제 설비 영향·운영 전체 안전성은 이번 기능의 수용 범위가 아니다. 기존 GitHub403은 재시도하지 않으며 로컬 기능 브랜치·커밋·복구 패키지만 만든다.
